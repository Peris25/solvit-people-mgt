## Audit findings and fixes

- Existing directory lacked region/category filtering and truncated lists at 500. Filters now use saved current/legacy fields and the complete authorized set. Search is literal, not user-supplied MongoDB regex. Duplicate canonical identifiers cause a review error rather than ambiguous profile resolution.
- Existing broad directory access did not implement the Brief's separate Operations/Account Management contact view. A narrowly scoped server guard resolves the saved FTE record and eligible department/status. Explicit M02 revocations still win. Contact-directory permission cannot call administration, assessments or private-document endpoints.
- Existing activation and generic profile updates could bypass induction; generic task completion could claim quiz/agreement completion. Activation now uses verified evidence; generic activation/score changes and completion of protected induction gates are rejected. Existing read-only scores and historical answers are preserved.
- Induction GET previously created tasks for privileged readers, and automation could duplicate checklist rows. GET is read-only; explicit initialization and registration automation share the locked, idempotent creator using canonical/legacy Solver aliases.
- Generic form outcome events previously set Solver progress regardless of quiz success. They no longer grant Solver induction or assessment success. Staged form routes cannot bypass the dedicated Solver quiz/evidence path.
- The old vehicle quiz contains five questions despite declaring 25 marks and a hardcoded 20-point pass mark, whereas the Brief requires configurable, versioned Parts A/B scoring. New submissions through that prototype are rejected with an explanation; historical submissions are retained and reviewable.
- Code-quiz submissions previously could be stored against an employee, without a canonical Solver subject. New attempts bind to the authenticated Solver. HR cannot impersonate a Solver's answers. Response schemas omit answer keys from non-HR callers.
- The mobile dashboard previously invented Standard/75/80/78/82 defaults from the user object. It now uses `/solvers/me`. Unknown metrics stay unknown; job counters are labelled as last-30-day figures rather than month-to-date, and no legacy client-rating scale is silently converted.
- Suspended/inactive/deactivated/ambiguous-state Solver accounts cannot use protected application routes with existing tokens. Authentication, password recovery/change and logout remain available through the existing recovery exceptions; refreshed tokens do not bypass protected-route checks. Registering/active accounts retain normal first-login password-change enforcement.
- Private applicant readers previously allowed Executive/IT/raw `solvers_manager` role names and exposed stored CV paths. Reads now require existing M02/M03 HR or qualified-manager access, use the caller's tenant, and omit private storage paths. HR-only requisition writes no longer grant IT personnel administration. CV download paths are resolved and checked inside their private root.
- Duplicate phone/email safeguards and the persistent integrity lock are reused, including normalized legacy phone comparisons. Duplicate job ratings are rejected when a job reference is supplied. Historical imports/accounts/assignments are not rewritten.
- The existing reporting catalogue referenced undefined scope variables; it now derives catalogue scope from the configured role/module. New Solver reports and exports use the existing redaction/formula-safe export infrastructure.

## Failure and recovery behaviour

New document publication and induction verifications remain `Pending_Audit` until their audit/notification writes succeed. An interrupted verification cannot satisfy activation. Activation records `activation_publication_state=Pending_Audit` before granting Active; own access remains blocked until audit, notification and checklist writes finish and publication becomes Ready. Interrupted assessment acknowledgements remain pending and cannot appear reviewed. Existing records without these new publication fields remain compatible.

There is no automatic lock expiry/removal or speculative rollback. Unexpected in-flight database failures retain the existing persistent integrity lock. For pending publication or a retained lock: stop all API/background writers; establish that the old worker/write is no longer running; inspect the affected IDs, evidence, partial records and audit entries using authorized operator access; reconcile missing audit/notification/checklist steps; publish Ready only after verified completion; remove a stale lock only under the existing controlled operator procedure. Do not restart a timed-out write concurrently or remove locks merely because they are old. No such recovery or database operation was run against production.
