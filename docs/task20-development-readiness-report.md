## Final pre-staging security implementation (supersedes initial code findings)

The user separately authorized local code fixes for leave-document security and cross-worker permission consistency. No production service/data, historical record/attachment, migration, index, commit, push or deployment was involved. Tasks 01-19 remain preserved.

### Leave document security closure

- Existing leave evidence retains its PDF/JPG/PNG and 5 MiB policy; shared Employee Document Centre filename/content/MIME validation and fail-closed ClamAV-compatible scanning now run before file persistence. Missing/unavailable/uncertain scanner returns 503; malware returns 422. Private random storage names, restrictive creation modes, exclusive file creation and root containment prevent user-controlled paths. Deployment filesystem ACLs still require validation on the real host.
- Upload metadata is initially `Pending_Audit`; an upload event in the existing `document_audit` collection must succeed before `Ready`. Interrupted/uncertain writes retain the existing integrity lock and file/metadata for controlled recovery. A pending attachment cannot be supplied as ready supporting evidence. Medical contents, original filenames and storage paths are not copied into audit previews or API responses.
- Every download resolves employee/document aliases and tenant first, then enforces owner-or-authorized-HR access and module grant. Direct managers and unrelated employees remain denied. Traversal, invalid stored names, missing files, hash mismatches and unpublished records fail closed.
- Every permitted download validates and scans the actual bounded bytes, including legacy attachments; a required download audit must succeed before response. The response serves exactly those inspected bytes rather than reopening a path after scanning. New files include a SHA-256 integrity marker; legacy rows are not backfilled, relinked or rewritten. Legacy malware or scanner outage prevents download while preserving the attachment and leave record.

### Multiworker permission closure

- Each request (including login, refresh, first-login and MFA recovery endpoints) reads persisted permission overrides/custom-role definitions before authorization. Health alone remains independent of permission storage. All workers therefore observe committed changes on the next request; no process cache TTL or polling lag remains.
- Context-local mapping proxies preserve existing synchronous helper/import interfaces while isolating each complete request snapshot. Readers no longer observe a global clear/refill or another concurrent request's settings. Missing/unavailable/duplicate/invalid configuration fails closed with 503 rather than granting fallback defaults. Script/test initialization remains explicit and is never the source of HTTP authorization.
- Custom roles now inherit effective base-role overrides, including revocations. An explicit null matrix update returns a denied effective cell immediately; deleting the override restores defaults. Account active status, role, password/session cutoff and MFA generation still come from live account state. Application MongoDB reads are explicitly pinned to primary, even if a URI supplies a secondary-preferred default.
- No new schema/index, change stream, Redis service or external credentials are required. Two primary collection reads per request trade caching performance for deterministic next-request enforcement; measure load in staging. Requests already authorized before a change are not retroactively cancelled; this is not a transaction across every account/settings/business write. Direct database writers and old API builds remain outside these guarantees.
- Regression coverage includes two separate long-running Python processes with independent FastAPI instances and startup caches, sharing only disposable localhost MongoDB. The test changes permissions through one instance, resets through the other, and checks revocation/restoration, inherited roles/grants, live MFA gates and account deactivation in both. Concurrent-context isolation, failed loads and malformed/duplicate settings are covered separately.
